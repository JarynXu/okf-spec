# Virtual Knowledge Namespace

Status: Draft

## Goal

Mounted Libraries participate in one logical hierarchical namespace that consumers can navigate consistently regardless of where or how the underlying knowledge is stored.

The namespace is an abstraction. A runtime may project it to a real filesystem, but filesystem materialization is not required.

## Principles

1. Every mounted Library has a stable namespace root.
2. Namespace paths identify logical knowledge nodes, not physical storage paths.
3. A node may be materialized, generated, remote, synthetic, or runtime-produced.
4. Consumers should be able to use the same logical identifiers through SDK, CLI, MCP, HTTP, or filesystem adapters.
5. Runtime-generated global catalog and status views may also appear as virtual nodes.

## Logical example

```text
/
├── libraries/
│   ├── mcx/
│   │   ├── architecture/
│   │   ├── interfaces/
│   │   └── standards/
│   ├── ddd/
│   └── project-context/
└── catalog/
```

This tree does not imply those nodes exist as local files.

For example:

```text
libraries/mcx/standards/...     -> object storage
libraries/mcx/catalog           -> generated by CatalogProvider
libraries/project-context/current -> computed from repository state
```

## Global catalog

A runtime MAY expose an aggregated global catalog generated from the catalogs of all mounted Libraries.

The global catalog SHOULD preserve Library boundaries while allowing progressive navigation from global scope to Library scope to topic scope to individual knowledge.

## Filesystem projections

A runtime MAY expose the namespace using FUSE, WinFsp, or another virtual filesystem mechanism.

Such projections are adapters only. Conformance MUST NOT depend on Linux filesystem semantics, Unix sockets, or any specific operating system implementation.
